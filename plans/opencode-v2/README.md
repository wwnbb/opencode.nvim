## Основание плана

Проверен рабочий checkout с базовым коммитом `58fcf3c` и уже существующими незакоммиченными исправлениями. Они являются частью исходного состояния: особенно важны изменения SSE-парсера, восстановления вопросов, конкурентных HTTP-снимков и хранения edit review. При реализации нельзя заменять их состоянием из `HEAD` или старой копии исходников.

Каталог `docs/` исключён правилом `docs/*` в `.gitignore`; поэтому планы находятся в `plans/opencode-v2/`. Локальная справочная копия OpenCode в `docs/opencode_source_code/opencode` датирована 13 августа 2026 и не является источником контракта 2.0.11.

Источники перечислены с версиями и контрольными суммами в [reference/sources.json](reference/sources.json). Машиночитаемый [реестр контрактов](reference/contract-inventory.json) отдельно фиксирует HTTP-операции, live events и durable event types. Использованы:

- опубликованные `@opencode/cli`, `@opencode/client`, `@opencode/plugin`, `@opencode/schema` версии **2.0.11**;
- [HTTP OpenAPI](https://opencode.ai/v2/openapi.json), полученная 21 сентября 2026;
- [документация миграции](https://opencode.ai/v2/docs/migrate-v1), [клиента](https://opencode.ai/v2/docs/build/client/), [серверных инструментов](https://opencode.ai/v2/docs/build/plugins/migrate-v1).

**Различать три уровня доказательств:**

1. **Подтверждено контрактом:** поля и маршруты из OpenAPI, опубликованные типы и реализация клиента 2.0.11.
2. **Проектное решение:** предлагаемые Lua-модули, внутренние структуры, состояния UI, порядок операций. Эти API ещё не существуют в репозитории.
3. **Требует runtime-проверки:** семантика, которую нельзя доказать типами: запуск CLI, последствия повторного prompt ID, правила ожидания permission, порядок снимков и событий, поведение файловых URI.

Онлайн-документация изменяется независимо от опубликованного пакета. Уже обнаружены расхождения примеров с 2.0.11: примеры `session.command` и `permission.reply` на обзорной странице не совпадают с HTTP-полями `name`/`text` и `decision`; описание `context.signal` отсутствует в опубликованном `ToolContext`. При конфликте опираться на установленную целевую версию, её generated client и фактический HTTP, а не копировать пример из документации.

## Общая архитектура

Сохранить Lua, nui.nvim, libuv, публичные команды Neovim и распределение владельцев состояния из [AGENTS.md](../../AGENTS.md).

```text
UI → actions.lua → init.lua / send.lua / session.lua
                         ↓
                   client/init.lua             публичный фасад
                         ↓
                   client/v2.lua               новые HTTP-контракты
                         ↓
                   client/http.lua → transport

SSE → client/sse.lua → protocol/v2/events.lua → обработчики событий
                                                  ↓
                                            sync.lua / session.lua
                                                  ↓
                                    существующие selectors и UI
```

Предлагаемые новые файлы, которые должны быть согласованно введены соответствующими этапами:

| Файл/модуль | Ответственность | Владелец этапа |
|---|---|---|
| `lua/opencode/client/v2.lua` | Маршруты, кодирование запросов, проверка формы ответов; без мутации хранилищ | 1 |
| `lua/opencode/protocol/v2/requests.lua` | Чистые преобразования prompt, model reference, location, command | 2 и 6 |
| `lua/opencode/protocol/v2/messages.lua` | Чистое преобразование истории и tool content в модель отображения | 3 |
| `lua/opencode/protocol/v2/events.lua` | Разбор envelope и классификация событий; без самостоятельного render/state | 3 |
| `lua/opencode/protocol/v2/forms.lua` | Схемы полей, преобразование ответов и ошибок форм | 4 |
| `lua/opencode/protocol/v2/catalogs.lua` | Нормализация providers/models/agents/MCP | 6 |

Серверный plugin для diff review получает отдельный публичный RPC-контракт из плана 5. Его события также проходят через общий SSE decoder; custom review и native permission сохраняют разные routing context. Новый RPC не является частью штатного OpenCode API.

Не требуется создавать все файлы заранее. Это целевые границы ответственности, а не поручение разбить код на пустые заглушки. Если reducer вынесен в подмодуль `sync/`, он остаётся частью владельца `sync.lua`, а не вторым независимым хранилищем.

### Инварианты

1. UI не импортирует `opencode.init` и не изменяет `state.lua`/`sync.lua` напрямую.
2. Все callback из TCP/SSE попадают на главный поток Neovim через существующие schedule helpers.
3. Внешний v2 DTO сохраняется достаточно полно для корректного восстановления; адаптер не выбрасывает идентификаторы, metadata, tool content, location и границы сообщений.
4. Факт принятия HTTP-запроса не равен завершению генерации.
5. Отсутствие объекта в частичной странице истории не означает его удаление.
6. Потеря соединения не превращает неизвестный результат в успешную отправку, отказ, разрешение или завершение.
7. Смена активной вкладки не меняет адресата уже начатой операции.
8. Только один согласованный путь меняет файлы во время review; ручные правки пользователя не перезаписываются повторным применением патча.
9. HTTP и SSE нормализуют одну и ту же сущность одинаково. После reconnect и загрузки истории виджеты сохраняют идентичность.
10. Ошибка обновления каталога не очищает рабочий список моделей и сохранённый выбор.

## Порядок выполнения

Порядок файлов отражает темы; выполнять их строго последовательно целиком не требуется.

| Этап | Работа | Условие перехода |
|---|---|---|
| A | Зафиксировать контракты и записать минимальные реальные HTTP/SSE fixtures | Известны версия, запуск, `/api/info`, создание сессии, один полный ответ |
| B | План 1: транспорт, location, базовые session/catalog endpoints | Можно подключиться, создать и прочитать сессию, получить страницы истории |
| C | Минимальная часть плана 6: agents/models/default; планы 2 и 3: отправка и текстовый поток | Один запрос, ответ, отмена и reconnect работают без дублирования |
| D | План 4 и план 5: permission/form и серверные инструменты | Проходят полные сценарии принятия, отклонения и частичного review |
| E | Остаток плана 6 и задачи/todo из плана 3 | Палитра, credentials, MCP, команды, fork/revert/compact работают |
| F | План 7: все UI-сценарии, полная тестовая матрица, установка в чистый профиль | Доказана готовность по критериям всех семи документов |

Первый рабочий чат — промежуточная веха, не завершение миграции. Полный перенос включает формы, review, историю, дочерние сессии, todo, авторизацию и установку серверных инструментов.

Целевой backend этой серии изменений — v2. Одновременная поддержка v1/v2 не предполагается автоматически. Сохранить предыдущий выпуск/ветку для v1; если понадобится dual-backend, отдельно расширить фасад и тестовую матрицу. Не смешивать эвристический fallback v1/v2 в каждом HTTP-методе.

## Вопросы, которые закрыть до соответствующей реализации

Это проверяемые технические задачи, а не причины останавливать подготовку или просить пользователя выбирать детали протокола.

| ID | Что неизвестно | Как получить доказательство | Где учитывается |
|---|---|---|---|
| R1 | CLI-флаги, объявление адреса, readiness и изоляция private server 2.0.11 | `--help`, запуск в временном профиле, захват stdout/stderr и `/api/info` | 1 |
| R2 | Повторный prompt с тем же `id`: дедупликация, conflict, последствия | Отправить одинаковый ID в тестовую сессию и сравнить inbox/history/events | 2 |
| R3 | Связь `ordinal` с `content[]`, snapshot/stream при reconnect, retry одного message ID | Записать трассы с несколькими текстовыми/reasoning/tool-блоками и разрывом сети | 3 |
| R4 | Native permission evaluation/reply/interrupt и порядок policy/hooks перед custom review; HTTP `permission.create` возвращает `effect`, но отсутствует в Plugin.Context | Контрактный тест allow/ask/deny/reply/interrupt; проверить отсутствие обхода policy и UX двух взаимодействий при RPC review | 4 и 5 |
| R5 | Отмена Promise tool и доступность `context.signal`, импорт `.txt` в runtime | Проверить установку и исполнение плагина на целевой версии | 5 |
| R6 | Представление subagent/tool metadata и источник todo в v2 | Реальные `task`/todo-сценарии; при отсутствии API реализовать сохранение через собственный server plugin | 3, 5, 7 |
| R7 | Допустимые URI вложений, индексы `mention` для Unicode | Изображение, файл/диапазон, кириллица и emoji в реальном prompt | 2 |
| R8 | Условные/внешние поля форм, валидация и смена состояния другим клиентом | Реальные формы всех типов, заведомо ошибочный ответ, ответ из второго клиента | 4 |
| R9 | Граница fork/revert; перенос старой истории исключён пользователем | Fixture до/после fork/revert проверены; migration status/import не входят в объём | 3 и 6 |

Закрытие пункта означает приложенный пример данных или тест с ожидаемым результатом. Комментарий «вероятно совместимо» не закрывает пункт.

## Проверка и выпуск

Существующие команды запускаются из корня репозитория:

```sh
./scripts/bootstrap-test-deps.sh
./tests/run.sh unit
./tests/run.sh checks
./tests/run.sh integration
./tests/run.sh smoke
./tests/run.sh tools
```

Bootstrap нужен только при отсутствии закреплённых зависимостей. Полный `./tests/run.sh` уже включает все перечисленные наборы; после зелёного полного прогона повторять их отдельно без изменений не требуется. Названия новых `*_v2_spec.lua` в планах — будущие тесты, а не существующие команды, которые уже можно выполнить.

Для проверки серверных инструментов текущие Bun-тесты с mock старого `tool()` недостаточны: требуется регистрация через реальный API 2.0.11 и запуск инструмента сервером. Для сетевой части нужны как детерминированные fixtures, так и один воспроизводимый интеграционный профиль с фактическим CLI 2.0.11. Реальные запросы к модели выполняются в отдельном тестовом проекте с настроенным тестовым провайдером; сам тестовый код не должен читать личные секреты или переписывать глобальную конфигурацию.

При выпуске указать минимально проверенную версию, установку server plugin, несовместимость текущего backend с v1 и известные ограничения. Сохранить способ вернуться к предыдущему выпуску плагина и копию прежней конфигурации. Не предполагать обратимость миграции серверной базы данных: восстановление данных — отдельная серверная операция, не `git checkout` плагина.

## Критерий завершения всей миграции

- [x] Закрыты критерии всех семи планов, включая server tools и нестандартные взаимодействия.
- [x] Каждый используемый HTTP-метод имеет проверку запроса, ответа и хотя бы одного ошибочного ответа.
- [x] Stream и HTTP history дают эквивалентное итоговое отображение и состояние.
- [x] Нет потери/дублирования после disconnect, переключения сессии и повторного получения снимка.
- [x] Review сохраняет ручные изменения и корректно отражает фактическое состояние диска.
- [x] Установка работает в чистом профиле; личная установка разработчика не является скрытой зависимостью.
- [x] Пройдены необходимые unit/checks/integration/smoke/tools и сценарии UI.
- [x] Документация установки и ограничения соответствуют реализованному состоянию.

Эти флажки относятся к **будущей миграции**. Создание настоящего комплекта планов не означает их выполнения.
